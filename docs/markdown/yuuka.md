# Yuuka

## ภาพรวม

`Yuuka` เป็น repository ที่รวบรวมความจริงเชิงโครงสร้างพื้นฐานของแพลตฟอร์มไว้มากที่สุด มันไม่ใช่ service ที่ผู้ใช้เรียกตรง ๆ และไม่ได้บรรจุ business logic หลัก แต่เป็นที่ที่บอกว่าระบบทั้งหมดถูกประกอบและวางตัวอย่างไร

ถ้าต้องการรู้ว่าแพลตฟอร์มต้องพึ่งบริการอะไรบ้าง รันอะไรในเครื่องพัฒนา รันอะไรในคลัสเตอร์ ใช้ observability stack แบบไหน หรือสภาพแวดล้อมต่าง ๆ ควรถูกจัดวางอย่างไร จุดเริ่มต้นที่ดีที่สุดคือ `Yuuka`

## สิ่งที่ Yuuka รวบรวมไว้

โดยสรุป repository นี้มีสี่กลุ่มเนื้อหาหลัก

กลุ่มแรกคือ service dependencies สำหรับการพัฒนาในเครื่องหรือ environment ที่ต้องการ bring up ระบบประกอบอย่างรวดเร็ว เช่น PostgreSQL, Redis, object storage และ observability stack

กลุ่มที่สองคือ deployment manifests สำหรับบริการหลักและบริการประกอบในสภาพแวดล้อมแบบ cluster ทำให้ทีมมองเห็นว่า `Midori`, `Momoi`, `Yuzu` และบริการอื่นถูก deploy อย่างไร

กลุ่มที่สามคือ configuration ด้าน observability ซึ่งรวมทั้ง metrics, logs และ traces ตลอดจนองค์ประกอบอย่าง Prometheus, Grafana, Loki, Jaeger และ collector ที่เกี่ยวข้อง

กลุ่มที่สี่คือเอกสาร ซึ่งไม่ได้มีแค่เอกสารโครงงาน แต่รวมถึงข้อมูลด้าน environment, database, observability และเอกสารสรุปสถาปัตยกรรมที่ใช้ในการสื่อสารภายในทีม

## มุมมองเชิงสถาปัตยกรรมที่ Yuuka ให้ได้

สิ่งที่ทำให้ `Yuuka` สำคัญคือมันช่วยตอบคำถามที่ repository อื่นตอบได้ไม่ครบ เช่น

- service ตัวไหนต้องรันคู่กัน
- service ตัวไหนต้องมี database หรือ cache อยู่ข้างหลัง
- service ตัวไหนรันในคลัสเตอร์ และตัวไหนควรอยู่บนเครื่องภายนอก
- observability data วิ่งไปทางไหน
- environment variables และ endpoint ระหว่าง service ควรสัมพันธ์กันอย่างไร

กล่าวอีกแบบหนึ่ง `Yuuka` เป็น repository ที่อธิบาย “แผนที่ของระบบ” มากกว่าตัวตนของ service ใด service หนึ่ง

## บริการประกอบที่ Yuuka ดูแลในระดับ topology

จากของจริงใน code base ปัจจุบัน เห็นได้ชัดว่า `Yuuka` รองรับบริการประกอบที่สำคัญมากหลายตัว เช่น

- PostgreSQL สำหรับข้อมูลหลัก
- Redis สำหรับ cache และ queue broker
- object storage แบบ S3-compatible สำหรับไฟล์
- Grafana สำหรับการดูแดชบอร์ด
- Prometheus สำหรับ metrics
- Loki สำหรับ logs
- Jaeger สำหรับ traces

สิ่งนี้มีความหมายมาก เพราะ application repositories หลักหลายตัวจะ start ไม่ได้หรือทำงานได้ไม่ครบ หากบริการในกลุ่มนี้ไม่พร้อม

## บทบาทต่อวงจรการพัฒนา

`Yuuka` มีบทบาทตั้งแต่เริ่มต้นพัฒนาไปจนถึงการดูแลระบบที่รันแล้ว

ในช่วงพัฒนา มันช่วยให้ทีม bring up dependencies ที่จำเป็นโดยไม่ต้องประกอบทีละตัวด้วยมือ

ในช่วงทดสอบ integration มันช่วยกำหนดว่าระบบแต่ละส่วนควรคุยกันด้วย URL, port และ credentials แบบใด

ในช่วง deploy มันเป็นแหล่ง truth ของ manifests และ topology

ในช่วง operation มันช่วยให้ทีมมองเห็น metrics, logs และ traces รวมทั้งทบทวนเอกสารเชิงสถาปัตยกรรมได้จากที่เดียว

## ความสำคัญของ observability ใน Yuuka

ระบบนี้ไม่ได้หยุดที่การมี application code ทำงานได้ แต่ให้ความสำคัญกับการมองเห็นสุขภาพของระบบค่อนข้างจริงจัง `Yuuka` จึงไม่ได้เก็บแค่ manifest ของ service หลัก แต่รวมส่วนของ observability stack ไว้อย่างเป็นรูปธรรม

ผลคือเมื่อ `Momoi` ตอบช้า `Yuzu` มีงานค้าง หรือ proxy ไม่ทำงาน ทีมมีโอกาสสูงที่จะหาหลักฐานจาก metrics, logs และ traces ได้แทนการเดาอย่างเดียว

ในระบบหลาย repository แบบนี้ observability ไม่ใช่ของเสริม แต่เป็นตัวช่วยเชื่อมการวิเคราะห์ข้าม service

## Yuuka ในฐานะ repository ที่สะท้อนความจริงของ deployment

หลายครั้ง code ในแต่ละ repository อาจบอกเพียงว่าบริการนั้น “สามารถ” ทำอะไรได้ แต่ `Yuuka` คือที่ที่มักเผยให้เห็นว่าระบบ “กำลังถูกวางใช้งานจริง” แบบใด เช่น environment หนึ่งอาจยังมี auth service แยกอยู่ หรือ topology บางส่วนอาจยังรองรับชิ้นส่วนที่เอกสารเชิงเรื่องเล่าล่าสุดลดบทบาทลงแล้ว

ด้วยเหตุนี้ `Yuuka` จึงมีค่าอย่างมากในงาน architecture review เพราะช่วยแยกความต่างระหว่างความตั้งใจเชิงเอกสารกับความจริงเชิง deployment

## ผลลัพธ์ที่ควรจะเป็นเมื่อ Yuuka ถูกใช้อย่างถูกต้อง

ถ้า repository นี้ถูกใช้งานอย่างถูกต้อง ระบบควรได้ประโยชน์ดังต่อไปนี้

- บริการประกอบในสภาพแวดล้อมพัฒนาสามารถเริ่มได้โดยไม่ต้องประกอบทีละตัวด้วยมือ
- manifests สำหรับ deployment พร้อมให้ทีมใช้งานและทบทวน topology ได้
- observability stack พร้อมรับข้อมูลจาก services หลัก
- เอกสารและ environment guidance ช่วยให้ทีมเข้าใจระบบตรงกันมากขึ้น
- ปัญหาที่เกิดจาก config mismatch ระหว่าง repo ลดลง

## อาการที่มักบอกว่าปัญหาอยู่ใน Yuuka หรือ infra topology

อาการที่มักย้อนกลับมาที่ `Yuuka` มีลักษณะกว้างกว่าปัญหาใน repo อื่น เช่น

- หลาย service ล้มพร้อมกันเพราะ dependency กลางไม่ขึ้น
- frontend, backend และ worker ใช้ค่าปลายทางคนละชุดกัน
- observability ว่างทั้งระบบแม้ service ดูเหมือนรันอยู่
- ระบบในเอกสารบอกอย่างหนึ่ง แต่ manifest ที่ deploy จริงชี้ไปอีกแบบหนึ่ง
- คนใหม่เริ่มงานแล้วเปิดระบบไม่ขึ้นเพราะไม่รู้ลำดับการ bring up dependencies

ปัญหาเหล่านี้มักไม่ใช่ bug ใน business logic โดยตรง แต่เป็นปัญหาเรื่องการจัดวางระบบ

## ขอบเขตของ Yuuka

`Yuuka` ไม่ได้เป็นเจ้าของกฎธุรกิจ ไม่ได้สร้าง VM เอง และไม่ใช่หน้าจอที่ผู้ใช้ใช้ทุกวัน แต่มันคือ repository ที่ทำให้ repository อื่นทำงานร่วมกันได้จริง ถ้าไม่มี `Yuuka` การเข้าใจและดูแลระบบทั้งชุดจะยากขึ้นมาก แม้แต่ service code จะยังอยู่ครบก็ตาม

## ความสัมพันธ์กับ repository อื่น

`Yuuka` เป็นเหมือนศูนย์กลางเชิง topology ที่เชื่อม `Midori`, `Momoi`, `Yuzu`, `Satsuki` และบริการประกอบทั้งหมดเข้าด้วยกัน อีกทั้งยังสะท้อนการมีอยู่ของ repository ประกอบอย่าง `Arisu` ด้วยในบางบริบท

## สรุปสั้น

`Yuuka` คือ repository สำหรับเข้าใจว่าแพลตฟอร์มถูกวางและดูแลอย่างไร ถ้า repository อื่นอธิบายว่า service หนึ่งทำงานอะไร `Yuuka` จะอธิบายว่า service เหล่านั้นอยู่ร่วมกันอย่างไรในโลกจริง
