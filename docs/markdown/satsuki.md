# Satsuki

## ภาพรวม

`Satsuki` เป็น automation service ที่ทำงานบนเครื่อง Nginx ภายนอกและมีบทบาทสำคัญมากใน production topology ของแพลตฟอร์ม แม้ผู้ใช้จะไม่เรียกมันโดยตรง แต่บริการนี้คือสิ่งที่ทำให้ “เครื่องที่ถูกสร้างแล้ว” กลายเป็น “เครื่องที่เข้าถึงได้จริง”

ในเชิงหน้าที่ `Satsuki` รับข้อมูลเชิงตรรกะจากฐานข้อมูล เช่น reverse proxy mappings, TCP routes, SSH public keys และสถานะของ instance แล้วแปลงข้อมูลเหล่านั้นให้เป็นไฟล์ config และไฟล์ระบบที่ Nginx กับ SSH ใช้งานได้จริง

## ทำไม Satsuki จึงสำคัญ

หากไม่มี `Satsuki` ระบบอาจยังสร้าง VM ได้สำเร็จจากมุมของ `Yuzu` แต่ผู้ใช้จะยังติดอยู่ในจุดที่เข้าถึงเครื่องไม่ได้ หรือเข้าได้ไม่สอดคล้องกับข้อมูลล่าสุดของระบบ

สำหรับแพลตฟอร์มประเภทนี้ การ provision VM อย่างเดียวไม่พอ ต้องมีชั้นที่ผูกเครื่องเหล่านั้นเข้ากับโลกภายนอกอย่างปลอดภัยและอัตโนมัติ `Satsuki` จึงทำหน้าที่เป็นสะพานเชื่อมระหว่างฐานข้อมูลของแพลตฟอร์มกับ reverse proxy host ที่รับ traffic จริง

## ลักษณะการออกแบบ

`Satsuki` ถูกออกแบบในลักษณะ automation daemon มากกว่า web service ทั่วไป ภายในแยกเป็นชั้น domain, application, infrastructure และ bootstrap อย่างชัดเจน ทำให้ logic การสร้าง config ไม่ผูกติดกับ shell command หรือ filesystem โดยตรงเกินไป

สิ่งนี้สำคัญมากเพราะระบบประเภทนี้มักเสียได้ง่ายหากทุกอย่างถูกเขียนเป็นสคริปต์ยาว ๆ ชุดเดียว การแยกบทบาทช่วยให้ reasoning เรื่องการ generate config, การ subscribe database notifications, การเขียนไฟล์ และการ reload service ถูกทดสอบและดูแลได้ง่ายขึ้น

## สิ่งที่ Satsuki ดูแลจริง

บริการนี้ดูแลสามเรื่องหลัก

เรื่องแรกคือ reverse proxy สำหรับ HTTP และ TCP การมี instance ในระบบไม่ได้แปลว่าผู้ใช้จะเข้าถึงได้ทันที ต้องมีการสร้างเส้นทางที่ผูก hostname หรือ port ภายนอกไปยังปลายทางของเครื่องนั้น

เรื่องที่สองคือ TLS tunneling และ TCP stream routing ซึ่งสำคัญสำหรับบริการที่ไม่ได้เป็น HTTP ตรง ๆ แต่ยังต้องถูกส่งผ่าน reverse proxy ชั้นหน้าอย่างปลอดภัย

เรื่องที่สามคือ SSH access `Satsuki` จะประกอบรายการ public keys ที่ควรได้รับอนุญาต แล้วสร้าง `authorized_keys` ให้สอดคล้องกับข้อมูลล่าสุดในระบบ

รวมกันแล้วบริการนี้จึงดูแลทั้ง “เข้าเว็บ”, “เข้า TCP service”, และ “เข้า shell” ของเครื่องปลายทาง

## วิธีการทำงานของ Satsuki

ลำดับการทำงานพื้นฐานของ `Satsuki` สามารถอธิบายได้ดังนี้

1. เริ่มต้น service และตรวจว่ามีโครงสร้างไฟล์ config ขั้นพื้นฐานพร้อมหรือไม่
2. เชื่อมต่อ PostgreSQL แบบที่รองรับ `LISTEN/NOTIFY`
3. ติดตั้งหรือใช้งาน database triggers ที่ส่งสัญญาณเมื่อข้อมูลสำคัญเปลี่ยน
4. subscribe ช่อง notification ที่เกี่ยวข้องกับ proxy และ SSH
5. เมื่อมีการเปลี่ยนแปลง จะอ่านข้อมูลล่าสุดจากฐานข้อมูล
6. ใช้ domain logic เพื่อประกอบไฟล์ config และ `authorized_keys`
7. เขียนไฟล์ลงตำแหน่งที่ระบบปฏิบัติการและ Nginx ใช้งานจริง
8. reload Nginx หรือ service ที่เกี่ยวข้องเมื่อจำเป็น

แนวคิดสำคัญของ flow นี้คือ `Satsuki` ไม่พยายามเดาจาก event อย่างเดียว แต่กลับไปอ่านสถานะล่าสุดจากฐานข้อมูลทุกครั้งที่ต้อง regenerate ของจริง วิธีนี้ช่วยลดความเสี่ยงจาก event ที่ตกหล่นหรือมาไม่ครบ

## Reverse Proxy ที่ Satsuki สร้างขึ้น

ในระบบนี้ reverse proxy ไม่ได้จำกัดแค่เว็บแอปพลิเคชันทั่วไป แต่รวมถึงการ route แบบ TCP และการทำ TLS tunneling ด้วย จึงมีความซับซ้อนกว่าการสร้าง virtual host ธรรมดา

Satsuki ต้องเข้าใจว่าบริการใดควรถูก expose แบบ HTTP, บริการใดต้องวิ่งผ่าน stream proxy, และบริการใดต้องอาศัยการจับคู่ host หรือ port กับ instance ปลายทาง การสร้าง config จึงไม่ใช่เพียงการใส่ชื่อ host ลงไฟล์ แต่เป็นการประกอบ topology ที่สัมพันธ์กับข้อมูลของ instance จริง

## SSH Access และ authorized_keys

อีกหน้าที่หนึ่งที่สำคัญมากคือการสร้าง `authorized_keys` จากข้อมูลผู้ใช้และสิทธิ์ที่บันทึกไว้ในระบบ แพลตฟอร์มนี้ไม่ได้พึ่งพาการแก้ไฟล์ SSH แบบ manual เป็นหลัก แต่ใช้ข้อมูลในฐานข้อมูลเป็น source of truth

ผลลัพธ์คือเมื่อผู้ใช้เพิ่มหรือแก้ SSH key ผ่านหน้าระบบ การเปลี่ยนแปลงจะค่อย ๆ ไหลไปยังเครื่อง reverse proxy หรือ bastion ผ่าน `Satsuki` แล้วกลายเป็นสิทธิ์เข้าถึงที่ใช้ได้จริง

นี่คือจุดที่เชื่อม `Midori`, `Momoi` และ `Satsuki` เข้าด้วยกันแบบทางอ้อม ผู้ใช้เห็นเพียงการบันทึก key ในหน้าเว็บ แต่เบื้องหลังมี service ที่แปลงข้อมูลให้กลายเป็นการเข้าถึงที่ทำงานได้จริง

## ผลลัพธ์ที่ควรจะเป็นเมื่อ Satsuki ทำงานถูกต้อง

ถ้า `Satsuki` อยู่ในสภาพพร้อมใช้งาน ควรเห็นผลแบบนี้

- service start ได้บนเครื่อง reverse proxy ภายนอก
- เมื่อมีการเปลี่ยนข้อมูล reverse proxy หรือ SSH key ระบบตอบสนองต่อการเปลี่ยนแปลงนั้นได้
- ไฟล์ config ที่เกี่ยวกับ HTTP และ TCP ถูกสร้างใหม่อย่างสม่ำเสมอ
- Nginx reload ผ่านและ route ใหม่เริ่มใช้งานได้
- `authorized_keys` สะท้อนข้อมูลล่าสุดของผู้ใช้
- ผู้ใช้เข้าถึง service ภายใน VM ผ่าน hostname หรือ port ที่ระบบกำหนดไว้ได้จริง

## อาการที่มักบอกว่า Satsuki มีปัญหา

อาการที่เจอบ่อยเมื่อ `Satsuki` ทำงานผิดพลาดมีหลายรูปแบบ

- instance ถูกสร้างแล้วแต่เข้าใช้งานผ่าน reverse proxy ไม่ได้
- ข้อมูล proxy mapping ในระบบถูกแก้แล้ว แต่ traffic ยังวิ่งไปปลายทางเก่า
- SSH key ถูกบันทึกแล้วแต่ผู้ใช้ยัง login ไม่ได้
- ไฟล์ config ถูกสร้างไม่ครบหรือ reload Nginx ไม่ผ่าน
- database notification ไม่ทำงาน ทำให้ระบบไม่ regenerate config ตามการเปลี่ยนแปลง
- service รันอยู่แต่ไม่มีสิทธิ์เขียนไฟล์หรือสั่ง reload service จริง

จุดสำคัญคืออาการเหล่านี้มักดูเหมือนปัญหาเครือข่ายหรือปัญหาเครื่องปลายทาง ทั้งที่จริงอาจอยู่ที่ชั้น automation ระหว่างกลางนี้

## ข้อจำกัดที่ต้องเข้าใจ

`Satsuki` ไม่ใช่ service ที่จะเห็นคุณค่าครบถ้วนในทุก dev machine เพราะมันต้องอยู่บนเครื่องที่มีบทบาทเป็น reverse proxy จริงและมีสิทธิ์แตะไฟล์ระบบได้ การทดสอบเฉพาะ logic อาจทำได้ใน local environment แต่คุณค่าที่แท้จริงจะปรากฏเมื่อมันได้รันใน host จริงพร้อม Nginx จริง

นอกจากนี้บริการนี้ยังพึ่งพาการเชื่อมต่อ PostgreSQL แบบรองรับ `LISTEN/NOTIFY` อย่างถูกต้อง หากมี proxy หรือ connection layer ที่ไม่รองรับพฤติกรรมนี้ ระบบอาจดูเหมือนเชื่อมฐานข้อมูลได้แต่ไม่ตอบสนองต่อ event

## ความสัมพันธ์กับ repository อื่น

`Satsuki` อ่านข้อมูลจากฐานข้อมูลที่ถูกจัดการโดย `Momoi`, สะท้อนผลของการมี instance ที่ `Yuzu` สร้างขึ้น, ทำให้สิ่งที่ `Midori` แสดงเรื่อง reverse proxy และ SSH access กลายเป็นของจริง, และพึ่งพา topology กับ deployment decisions ที่สรุปไว้ใน `Yuuka`

## สรุปสั้น

`Satsuki` คือบริการที่ทำให้โครงสร้างพื้นฐานของแพลตฟอร์ม “เข้าถึงได้จริง” ถ้า `Yuzu` ทำหน้าที่สร้างเครื่อง `Satsuki` ก็ทำหน้าที่เปิดทางให้คนเข้าไปใช้เครื่องนั้นได้อย่างสอดคล้องกับข้อมูลและสิทธิ์ในระบบ
