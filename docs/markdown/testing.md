# Testing

## ภาพรวม

`Testing` เป็น utility repository สำหรับช่วยทดสอบระบบจากมุมมองของผู้ใช้จริงมากกว่าจากมุมของ unit test หรือ service-level test มันถูกใช้เพื่อสร้างข้อมูลผู้ใช้ทดสอบ เรียก auth flows และเก็บ session ในรูปแบบที่นำไปใช้งานต่อได้

จุดเด่นของ repository นี้คือมันสะท้อนวิธีคิดเชิงปฏิบัติของทีม กล่าวคือแทนที่จะทดสอบทุกอย่างผ่าน mock หรือผ่าน test framework เท่านั้น ก็มีเครื่องมือเล็ก ๆ ที่ใช้จำลองผู้ใช้จำนวนมากเพื่อดูว่าระบบตอบสนองอย่างไรในโลกจริง

## สิ่งที่ Testing ทำได้ในปัจจุบัน

จากสภาพโค้ดปัจจุบัน repository นี้ทำงานได้ในลักษณะต่อไปนี้

- สร้างรหัสนักศึกษาแบบสุ่มตามรูปแบบที่ระบบยอมรับ
- สร้างอีเมลและรหัสผ่านของผู้ใช้ทดสอบ
- เรียก auth endpoints ของระบบผ่าน client ที่อิง API contract
- ใช้งาน flow การสมัครและเข้าสู่ระบบ
- เก็บ cookies ของผู้ใช้แต่ละคนออกมาเป็นไฟล์เพื่อใช้จำลอง session ในขั้นตอนต่อไป

นี่ไม่ใช่แค่ helper เล็ก ๆ แต่เป็นสะพานเชื่อมระหว่างการสร้าง test data กับการทดสอบ integration แบบจับต้องได้

## รูปแบบการใช้งานโดยทั่วไป

ลำดับที่ repository นี้ตั้งใจรองรับมีประมาณนี้

1. สร้างชุดข้อมูลผู้ใช้ทดสอบจำนวนหนึ่ง
2. บันทึกรายการผู้ใช้เหล่านั้นไว้ในไฟล์ข้อมูล
3. เรียก sign-up เพื่อสร้างผู้ใช้ในระบบจริงหรือ environment ที่กำลังทดสอบ
4. เรียก sign-in เพื่อรับ session
5. แยก cookies ของผู้ใช้แต่ละคนออกเป็นไฟล์
6. นำ cookies เหล่านั้นไปใช้ทดสอบ flow อื่นต่อ

วิธีคิดนี้มีประโยชน์มากเมื่ออยากจำลองว่าผู้ใช้หลายคนจะ interact กับระบบอย่างไร โดยเฉพาะในระบบที่ role, session และ auth policy มีผลต่อสิ่งที่ผู้ใช้เห็น

## จุดเด่นของ Testing ในเชิงวิศวกรรม

repository นี้แม้จะไม่ใหญ่ แต่มีคุณค่าหลายด้าน

ด้านแรกคือช่วยลดเวลาที่ต้องใช้สร้าง test users ด้วยมือ โดยเฉพาะเมื่อแพลตฟอร์มมีรูปแบบอีเมลหรือข้อมูลผู้ใช้ที่เฉพาะเจาะจง

ด้านที่สองคือช่วยให้ทีมทดสอบ auth flow แบบ end-to-end ได้เร็วขึ้น เพราะไม่ต้อง login ผ่านหน้าเว็บทุกครั้ง

ด้านที่สามคือช่วยต่อยอดไปสู่การทดสอบ API อื่นในสภาวะที่มี session จริง เช่น การสร้างคำร้อง การดึงรายการเครื่อง หรือการทดสอบสิทธิ์ของผู้ใช้หลายบทบาท

## ข้อจำกัดของ implementation ปัจจุบัน

แม้ repository นี้มีประโยชน์ แต่ก็ยังมีข้อจำกัดชัดเจน

ส่วนหนึ่งของ logic ยังถูกคอมเมนต์ไว้ ทำให้การใช้งานจริงต้องอาศัยการเปิดใช้สคริปต์ด้วยความเข้าใจของผู้ใช้

นอกจากนี้ยังมีการกำหนดปลายทางของระบบที่จะทดสอบไว้ค่อนข้างตรงตัว หาก environment เปลี่ยน ผู้ใช้ต้องรู้เองว่าต้องปรับอะไรบ้าง

อีกจุดหนึ่งคือการเขียน cookies ออกมาเป็นไฟล์มีประโยชน์มากในเชิงทดสอบ แต่ก็ต้องระวังเรื่องความปลอดภัย ความเป็นส่วนตัว และการไม่เผลอนำข้อมูล session จริงไปใช้ผิด environment

## ผลลัพธ์ที่ควรจะเป็นเมื่อ Testing ใช้งานได้ถูกต้อง

ถ้าใช้งาน repository นี้ได้ตามที่ตั้งใจ ควรเห็นผลดังนี้

- สามารถสร้างผู้ใช้ทดสอบจำนวนมากได้โดยไม่ต้องทำมือ
- auth endpoints ตอบกลับสอดคล้องกับข้อมูลที่สร้างขึ้น
- ผู้ใช้ที่ลงทะเบียนแล้วสามารถ sign in และสร้าง cookies ได้
- ทีมพัฒนานำ cookies เหล่านั้นไปใช้ทดสอบ flow อื่นของระบบต่อได้
- การทดสอบเชิง integration ทำได้เร็วขึ้นโดยไม่ต้องพึ่ง UI ทุกขั้นตอน

## อาการที่มักบอกว่า Testing ต้องถูกปรับก่อนใช้

อาการที่พบได้บ่อยเมื่อ repository นี้ไม่พร้อมใช้มีดังนี้

- base URL ชี้ไป environment ที่ไม่ถูกต้อง
- auth flow ของระบบเปลี่ยนแต่สคริปต์ยังใช้ขั้นตอนเก่า
- รูปแบบอีเมลผู้ใช้ทดสอบไม่ผ่านนโยบายของระบบ
- cookies ถูกสร้างไม่สำเร็จเพราะ endpoint หรือ response format เปลี่ยน
- ผู้ใช้ทดสอบถูกสร้างแล้ว แต่ role หรือสิทธิ์ไม่ตรงกับสิ่งที่ต้องการจำลอง

นี่เป็นข้อเตือนว่าถึงแม้ repository จะเล็ก แต่ก็ผูกกับความจริงของระบบมาก และต้องปรับตาม environment เสมอ

## สถานะของ Testing เมื่อเทียบกับระบบหลัก

`Testing` ไม่ได้เป็นส่วนหนึ่งของ runtime หลักและไม่ได้ถูก deploy เป็นบริการ แต่มีคุณค่ามากในฐานะเครื่องมือประกอบสำหรับ quality assurance, exploratory testing และการสร้างสถานการณ์จำลองที่ใช้คนจริงทำด้วยมือจะเสียเวลามาก

มันจึงควรถูกมองเป็นเครื่องมือช่างของทีม มากกว่าจะเป็นส่วนของสถาปัตยกรรมที่ผู้ใช้ปลายทางมองเห็น

## สรุปสั้น

`Testing` คือ repository สำหรับจำลองผู้ใช้และตรวจ flow จริงของระบบจากมุมของ session และ auth มันไม่ใช่ service หลัก แต่ช่วยให้การทดสอบแบบ end-to-end และ integration มีความเป็นรูปธรรมมากขึ้นอย่างชัดเจน
