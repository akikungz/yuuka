# Yuzu

## ภาพรวม

`Yuzu` เป็น background worker ที่รับผิดชอบการลงมือทำงานกับ VM บน Proxmox VE จริง ถ้า `Momoi` เป็นคนตัดสินว่างานควรเกิดหรือไม่ `Yuzu` คือคนที่เอาคำตัดสินนั้นไปปฏิบัติให้เกิดผลบน infrastructure

ความสำคัญของ `Yuzu` อยู่ที่การเชื่อมโลกของข้อมูลกับโลกของเครื่องจริง มันไม่เพียงอ่าน job จาก queue แล้วเรียก API เท่านั้น แต่ต้องเข้าใจสถานะล่าสุดของ instance, เลือกจังหวะที่เหมาะสมในการทำงาน, ป้องกันงานชนกัน และอัปเดตผลลัพธ์กลับไปยังฐานข้อมูลให้สอดคล้องกับสิ่งที่เกิดขึ้นจริง

## ขอบเขตความรับผิดชอบของ Yuzu

หน้าที่หลักของ `Yuzu` มีสามกลุ่ม

กลุ่มแรกคือ provisioning ซึ่งรวมถึงการเตรียมข้อมูลที่จำเป็น เลือกทรัพยากรปลายทาง สร้าง VM ใหม่จาก template แบบ linked clone ตั้งค่าเครื่อง และบันทึกผลลัพธ์กลับสู่ระบบ

กลุ่มที่สองคือ deprovisioning ซึ่งทำหน้าที่ปิดวงจรชีวิตของ VM เดิม ลบทรัพยากรที่ไม่ควรค้างอยู่ และทำให้สถานะในระบบกลับมาอยู่ในรูปที่สะอาดที่สุดเท่าที่จะทำได้

กลุ่มที่สามคือ power operations เช่น start, stop หรือ restart ซึ่งดูเหมือนง่าย แต่ต้องทำบนข้อมูลล่าสุดและอยู่ภายใต้กติกาเรื่อง lock เช่นเดียวกับงานอื่น

ทั้งหมดนี้เกิดขึ้นโดยที่ `Yuzu` ไม่ใช่ผู้ตัดสินกฎทางธุรกิจเอง มันรับคำสั่งที่ผ่านการอนุมัติและการตรวจสิทธิ์มาแล้วจาก `Momoi`

## ภาพโครงสร้างภายใน

ภายใน `Yuzu` มีการแยกส่วนอย่างเป็นระบบพอสมควร

มีชั้น use case ที่บอกพฤติกรรมหลักของ worker อย่างชัดเจน มีชั้น port และ adapter สำหรับคุยกับ Redis, PostgreSQL และ Proxmox API มีชั้น queue worker ที่รับผิดชอบแต่ละประเภทงาน และมีชั้น observability กับ config ที่ช่วยให้ service นี้ถูกปรับแต่งและสังเกตอาการได้ใน production

ผลของการแยกชั้นแบบนี้คือ logic ที่เกี่ยวกับการสร้างหรือลบ VM ไม่ได้ปะปนกับรายละเอียดของ queue หรือ Redis มากเกินไป และยังช่วยให้กฎเรื่อง locking กับ state transition ถูกมองเห็นชัดกว่า worker แบบ script เดียวจบ

## ประเภทของงานที่ Yuzu ประมวลผล

ใน implementation ปัจจุบัน `Yuzu` ดูแลงานหลักอยู่สามประเภท

- งานสร้างเครื่องใหม่
- งานลบหรือยกเลิกเครื่องเดิม
- งานเปลี่ยนสถานะการเปิดปิดเครื่อง

การแยกเป็นหลายคิวทำให้แต่ละประเภทงานมี throughput และ tuning ของตัวเองได้ ไม่จำเป็นต้องให้ทุกอย่างแย่ง worker concurrency ชุดเดียวกัน

## ลำดับการทำงานของ provision

สำหรับงานสร้างเครื่องใหม่ ลำดับโดยสังเขปของ `Yuzu` จะเป็นดังนี้

1. ดึง job จาก queue
2. อ่านข้อมูลล่าสุดของ instance จากฐานข้อมูล
3. ตรวจว่าข้อมูลที่ต้องใช้ยังครบและอยู่ในสถานะที่สร้างต่อได้
4. สร้างบริบทของงาน เช่น hostname และข้อมูลประกอบอื่น
5. หา VMID ปลายทางที่ยังว่าง และเลือก node เป้าหมายตามนโยบายของระบบ
6. ทำ linked clone จาก template ที่กำหนด
7. ตั้งค่าทรัพยากรของ VM เช่น CPU, RAM, network หรือค่าที่จำเป็นอื่น
8. เริ่มเครื่องและรอให้การทำงานสำคัญเสร็จ
9. บันทึกข้อมูลสำคัญกลับลงฐานข้อมูล
10. ล้าง cache ที่เกี่ยวข้องเพื่อให้ frontend เห็นข้อมูลล่าสุด

สิ่งที่ควรสังเกตคือ provisioning ไม่ได้เป็นคำสั่งเดี่ยว แต่มันเป็นชุดของ state transition หลายขั้น หากขั้นใดขั้นหนึ่งล้มเหลว `Yuzu` ต้องทำให้ข้อมูลในระบบสะท้อนความล้มเหลวนั้นอย่างชัดเจน

## ลำดับการทำงานของ deprovision

งาน deprovision มีความสำคัญไม่แพ้งานสร้าง เพราะหากลบไม่ครบ ระบบจะเหลือทรัพยากรค้างที่ทำให้ต้นทุนและความสอดคล้องของข้อมูลเสียหาย

ลำดับทั่วไปคือดึงข้อมูล instance ล่าสุด ตรวจว่ามี VM ที่ต้องลบจริงหรือไม่ ถ้ามีจะสั่งปิดหรือลบตามขั้นตอนที่เหมาะสม จากนั้นจึงอัปเดตสถานะในฐานข้อมูล ล้าง cache และทำให้ระบบมองเห็นว่า instance นั้นไม่ใช่เครื่องที่พร้อมใช้งานอีกต่อไป

ในบางกรณี deprovision ต้องรับมือกับสถานะที่โลกความจริงกับฐานข้อมูลไม่ตรงกัน เช่น ฐานข้อมูลบอกว่ามี VM แต่ Proxmox ไม่พบแล้ว หรือกลับกัน นี่คือเหตุผลที่ worker นี้ต้องระมัดระวังเรื่อง state reconciliation พอสมควร

## ลำดับการทำงานของ toggle status

งานเปลี่ยนสถานะเครื่องมีลักษณะสั้นกว่าสองงานแรก แต่ยังสำคัญเพราะแตะเครื่องจริงเช่นกัน โดยต้องอ่านข้อมูลล่าสุดของ instance ก่อนเสมอ ตรวจว่ามี VM ที่อ้างอิงอยู่จริง แล้วจึงสั่ง start, stop หรือ restart ตามคำขอและเงื่อนไขของสถานะปัจจุบัน

แม้งานลักษณะนี้จะดูเบา แต่ถ้าปล่อยให้หลายคำสั่งวิ่งชนกันบน VM เดียวกัน จะสร้างอาการเสียแบบคาดเดายากได้ง่ายมาก จึงต้องอาศัย lock เหมือนกับงานอื่น

## ระบบคิวและแนวคิดเรื่อง concurrency

`Yuzu` รุ่นปัจจุบันไม่ได้มีข้อจำกัดแบบง่าย ๆ ว่า “หนึ่ง pod ทำได้หนึ่งงาน” อีกต่อไป เพราะ worker แต่ละคิวรองรับการตั้งค่า concurrency ของตัวเองผ่าน environment variables

ในค่าปริยายตอนนี้ provision ใช้ concurrency ระดับ 5, deprovision ใช้ 5 และ toggle-status ใช้ 10 นั่นหมายความว่าเมื่อมีหลาย pod รวมกัน throughput เชิงทฤษฎีของแต่ละคิวจะเป็นผลคูณของจำนวน pod กับ concurrency ของคิวนั้น

ตัวอย่างเช่น หากมี `Yuzu` อยู่ 3 pods และไม่มี resource contention เลย ความสามารถเชิงทฤษฎีจะอยู่ประมาณนี้

- provision ได้ประมาณ 15 งานพร้อมกัน
- deprovision ได้ประมาณ 15 งานพร้อมกัน
- toggle-status ได้ประมาณ 30 งานพร้อมกัน

อย่างไรก็ตาม ตัวเลขนี้เป็นเพียงเพดานเชิงทฤษฎี ไม่ใช่ผลลัพธ์ที่รับประกันได้เสมอ เพราะของจริงยังติดเรื่อง lock, network latency, ความเร็วของ Proxmox, ภาระของ database และความยาวของงานแต่ละประเภท

## กลไก lock ใน implementation ปัจจุบัน

หัวใจสำคัญของ `Yuzu` รุ่นล่าสุดคือ distributed locking บน Redis ซึ่งใช้เพื่อกันไม่ให้หลายงานชนกันแบบทำลายความถูกต้องของ state

กติกาปัจจุบันคือมี lock ตาม `instanceId` และตาม `VMID`

lock ตาม `instanceId` ใช้กันงานต่างประเภทที่อ้างถึง instance ตัวเดียวกันไม่ให้วิ่งพร้อมกัน เช่น provision, deprovision และ toggle-status ของเครื่องเดียวกัน

lock ตาม `VMID` ใช้กันงานที่แตะ VM ตัวเดียวกันจริง ๆ ไม่ให้ชนกันในช่วง critical section ของการปฏิบัติงาน

ผลลัพธ์ของกติกานี้คือ

- งานที่อ้างถึง instance เดียวกันไม่ควรวิ่งซ้อนกัน
- งานที่แตะ VMID เดียวกันไม่ควรวิ่งพร้อมกัน
- งานคนละ VM ยังทำพร้อมกันได้แม้อยู่บน Proxmox node เดียวกัน
- linked clone จาก template เดียวกันยังทำงานขนานกันได้ เพราะ lock ไม่ได้จับ template ต้นทาง แต่จับ VM ปลายทางที่กำลังจะถูกสร้าง

นี่เป็นความเปลี่ยนแปลงสำคัญจากแนวคิดที่ lock ตาม node หรือ storage เพราะช่วยให้ระบบขนานงานได้ดีขึ้นโดยยังคงความปลอดภัยของ state ที่สำคัญไว้

## สิ่งที่ Yuzu ต้องพึ่งพาเพื่อทำงานได้

`Yuzu` ต้องพึ่งพาองค์ประกอบภายนอกหลายตัวพร้อมกัน

- ต้องเชื่อม Redis ได้เพื่อดึงงานและใช้ distributed lock
- ต้องเชื่อม PostgreSQL ได้เพื่ออ่านและเขียนสถานะล่าสุด
- ต้องเชื่อม Proxmox VE ได้จริงพร้อม credential ที่ใช้ได้
- ต้องมีข้อมูลจาก `Momoi` ในฐานข้อมูลที่สมบูรณ์พอจะตัดสินว่าแต่ละงานควรทำอะไร

ดังนั้นเวลางานไม่เดิน สาเหตุอาจมาจาก queue, database, network, credential หรือ logic ด้าน state transition ก็ได้ ไม่ใช่ปัญหาใน worker code อย่างเดียว

## ผลลัพธ์ที่ควรจะเป็นเมื่อ Yuzu ทำงานถูกต้อง

ถ้า `Yuzu` ทำงานสมบูรณ์ ควรเห็นสิ่งต่อไปนี้

- worker ของทุกคิว start ได้และพร้อมรับงาน
- งานที่ถูก enqueue เข้ามาเริ่มถูกดึงไปประมวลผลโดยไม่ค้างยาวผิดปกติ
- การสร้างเครื่องใหม่ทำให้เกิด VM จริงพร้อมข้อมูลที่สอดคล้องกันในฐานข้อมูล
- การลบเครื่องทำให้ทั้งฐานข้อมูลและ Proxmox สะท้อนสถานะเดียวกันมากที่สุด
- การเปิดปิดเครื่องทำงานได้และสถานะอัปเดตกลับมาอย่างถูกต้อง
- งานที่ชน `instanceId` หรือ `VMID` เดียวกันไม่วิ่งพร้อมกัน
- งานคนละ VM ยังใช้ concurrency ร่วมกันได้อย่างมีประสิทธิภาพ
- logs และ metrics บอกได้ว่า job ใดสำเร็จ ล้มเหลว หรือรอ lock

## อาการที่มักบอกว่า Yuzu มีปัญหา

มีหลายอาการที่ควรพุ่งมาดู `Yuzu` ก่อน

- queue มีงานรอแต่ไม่มีใครหยิบไปทำ
- ผู้ใช้ส่งคำขอสำเร็จแล้วแต่ VM ไม่เกิด
- VM ถูกสร้างแล้วแต่ฐานข้อมูลไม่อัปเดต หรือกลับกัน
- deprovision ทำให้ทรัพยากรบางส่วนค้าง
- lock timeout เกิดบ่อยจน throughput ต่ำผิดปกติ
- งานจำนวนมากรอคิวทั้งที่ pod มีพอ แต่ concurrency ถูกตั้งต่ำเกินไป
- งานที่ควรขนานได้กลับติดกันเพราะ lock scope กว้างเกินไป
- worker ตอบสนองดีแต่คุยกับ Proxmox ไม่ผ่าน

## การตีความผลลัพธ์เมื่อมีหลาย Pod

ในระบบที่รันหลาย pods สิ่งที่ต้องเข้าใจคือ “จำนวนงานที่ทำพร้อมกันจริง” จะขึ้นกับสามตัวแปรพร้อมกัน ได้แก่ จำนวน pods, ค่า concurrency ของแต่ละคิว และรูปแบบการชนกันของ resource

ดังนั้นถ้ามี 3 pods แต่ทุกงานชน `instanceId` เดียวกัน ระบบก็จะไม่สามารถทำพร้อมกันได้ตามเพดานเชิงทฤษฎี ในทางกลับกัน หากงานกระจายไปคนละ instance และคนละ VMID ระบบจะใช้ประโยชน์จาก concurrency ได้ใกล้เพดานมากขึ้น

จุดนี้สำคัญมากในการอ่านผล benchmark หรืออธิบายพฤติกรรมของระบบให้ตรงกับของจริง

## ขอบเขตที่ Yuzu ไม่ควรรับผิดชอบ

`Yuzu` ไม่ควรเป็นผู้ตัดสินว่า request ควรถูกอนุมัติหรือไม่ และไม่ควรเป็นผู้กำหนด policy ทางธุรกิจ เช่น ระยะเวลาที่ผู้ใช้ใช้เครื่องได้หรือสิทธิ์ของผู้ใช้แต่ละกลุ่ม สิ่งเหล่านั้นเป็นหน้าที่ของ `Momoi`

ในทำนองเดียวกัน `Yuzu` ก็ไม่ควรไปสร้างไฟล์ reverse proxy หรือ `authorized_keys` เอง เพราะนั่นเป็นขอบเขตของ `Satsuki`

## ความสัมพันธ์กับ repository อื่น

`Yuzu` รับงานจาก `Momoi`, อ่านและเขียนสถานะผ่าน PostgreSQL, ใช้ Redis ทั้งในฐานะ queue broker และ lock backend, ทำงานกับ Proxmox VE โดยตรง, และทำให้ผู้ใช้เห็นผลลัพธ์ผ่านข้อมูลที่ `Midori` ดึงจาก backend ส่วน topology ของการรัน pods และ environment ที่ใช้จริงขึ้นกับ `Yuuka`

## สรุปสั้น

`Yuzu` คือหัวใจของฝั่ง execution มันเป็นส่วนที่เปลี่ยนคำว่า “อนุมัติแล้ว” ให้กลายเป็น VM จริง พร้อมกับรักษาความถูกต้องของ state ท่ามกลางงานที่วิ่งพร้อมกันหลายคิว หลาย pod และหลายทรัพยากร
