# Momoi

## ภาพรวม

`Momoi` เป็น core API และศูนย์กลาง business logic ของแพลตฟอร์ม ถ้าต้องเลือก repository เดียวที่อธิบายว่าระบบ “คิด” อย่างไร คำตอบคือ `Momoi` เพราะส่วนนี้เป็นผู้ตัดสินว่าคำสั่งใดทำได้หรือไม่ได้ ใครมีสิทธิ์ทำอะไร ข้อมูลใดควรถูกบันทึก และเมื่อใดที่ต้องส่งงานต่อไปยัง worker

ในเชิงสถาปัตยกรรม `Momoi` คือจุดเชื่อมระหว่าง frontend, ฐานข้อมูล, queue, storage และ monitoring มันรับคำขอจากผู้ใช้ผ่าน `Midori`, เปลี่ยนคำขอนั้นให้กลายเป็นกฎทางธุรกิจที่บังคับได้, แล้วจึงส่งผลลัพธ์ไปยังระบบส่วนอื่น

## สิ่งที่ Momoi รับผิดชอบจริง

`Momoi` ไม่ได้ทำแค่เปิด endpoint แล้วส่ง query เข้า database แต่รับผิดชอบโดเมนหลักของแพลตฟอร์มแทบทั้งหมด เช่น

- ข้อมูลทางวิชาการ เช่น รายวิชา ภาคการศึกษา และรายชื่อผู้สอน
- การสร้าง ดู อนุมัติ และติดตามคำร้องขอเครื่องเสมือน
- การจัดการ extended requests หรือคำร้องที่ต่อยอดจากคำร้องหลัก
- การดูแล instance ที่ถูกสร้างแล้ว รวมถึง reverse proxy และ audit logs
- การจัดการ SSH key และข้อมูลผู้ใช้ในระดับแพลตฟอร์ม
- การจัดการพื้นที่เก็บไฟล์ สิทธิ์การเข้าถึง และ presigned URLs
- การเปิด monitoring endpoints เพื่อให้ frontend สอบถามข้อมูลจาก Prometheus ได้
- การให้ข้อมูล autocomplete หรือข้อมูลช่วยเลือกใน UI

เมื่อเห็นขอบเขตนี้จะชัดว่า `Momoi` คือระบบธุรกิจของแพลตฟอร์มจริง ๆ ไม่ใช่เพียงชั้น transport

## แนวทางการออกแบบภายใน

จาก code base ปัจจุบัน `Momoi` ถูกจัดเป็นหลายชั้นอย่างมีวินัยพอสมควร มีทั้งชั้น route, service, module, infrastructure, model และ utility แยกจากกัน จุดแข็งของแนวทางนี้คือทำให้ business rule ไม่ต้องไปผูกติดอยู่กับ framework หรือฐานข้อมูลมากเกินไป

โดเมนหลักถูกแยกออกจากกันอย่างชัดเจน เช่น domain ด้าน request ไม่ปะปนกับ domain ด้าน storage และ domain ด้าน monitoring ก็ไม่ถูกยัดรวมกับ route ธรรมดา วิธีนี้สำคัญมากสำหรับระบบที่โตเกินกว่าจะดูแลด้วย controller ชุดเดียว

อีกประเด็นที่เด่นคือ `Momoi` ให้ความสำคัญกับ observability และ API contract มากกว่าระบบทั่วไป มันไม่ได้เพียงตอบ JSON กลับไป แต่มีการวัด request metrics, เก็บ telemetry และเปิดข้อมูล OpenAPI เพื่อให้ frontend ใช้ประโยชน์ต่อได้อย่างเป็นระบบ

## ภาพของโดเมนภายใน Momoi

เพื่อให้เห็นความลึกของ repository นี้ชัดขึ้น สามารถมองโดเมนภายในเป็นกลุ่มใหญ่ ๆ ได้ดังนี้

กลุ่มแรกคือโดเมนเกี่ยวกับผู้ใช้และบริบทการเรียนการสอน ซึ่งครอบคลุมผู้สอน รายวิชา ภาคการศึกษา การค้นหาข้อมูลช่วยกรอกแบบฟอร์ม และกฎที่กำหนดว่าผู้ใช้แต่ละบทบาทควรเห็นอะไร

กลุ่มที่สองคือโดเมนเกี่ยวกับคำร้องและเครื่องเสมือน ซึ่งเริ่มตั้งแต่การสร้าง request, การอนุมัติ, การผูก request เข้ากับ instance, การดู audit logs, การ reprovision, การ promote หรือการตั้งค่า reverse proxy ของ instance

กลุ่มที่สามคือโดเมนด้าน storage ซึ่งไม่ใช่เพียงการเก็บ metadata ของไฟล์ แต่รวมถึงสิทธิ์การเข้าถึง การคัดลอก ย้าย ลบ ดาวน์โหลด และการสร้าง presigned URL เพื่อเชื่อมกับ object storage จริง

กลุ่มที่สี่คือโดเมนด้าน monitoring ซึ่งทำหน้าที่เป็นตัวกลางให้ frontend เรียก query แบบปลอดภัยไปยังระบบ observability โดยไม่ต้องให้ผู้ใช้คุยกับ Prometheus ตรง ๆ

## ลำดับการทำงานของ request ทั่วไป

เมื่อ request หนึ่งเข้ามาที่ `Momoi` โดยทั่วไปจะมีลำดับดังนี้

1. รับ request จาก `Midori` หรือ client อื่น
2. ผ่าน middleware สำหรับ CORS, telemetry, request metrics และ auth integration
3. แยกเส้นทางไปยังโดเมนที่เกี่ยวข้อง
4. ตรวจ session, role และเงื่อนไขเชิงธุรกิจ
5. อ่านหรือเขียนข้อมูลผ่าน PostgreSQL
6. ใช้ cache เมื่อเหมาะสม และล้าง cache เมื่อข้อมูลสำคัญเปลี่ยน
7. ถ้างานนั้นเป็นงานระยะยาว เช่น provisioning หรือ deprovisioning จะส่ง job เข้า Redis/BullMQ
8. ส่งผลลัพธ์กลับไปยัง frontend ในรูปแบบที่ผู้ใช้เข้าใจได้

สิ่งที่สำคัญคือ `Momoi` แยก “งานที่ตอบกลับได้ทันที” กับ “งานที่ต้องทำต่อภายหลัง” อย่างชัดเจน นี่คือหัวใจที่ทำให้ระบบมีทั้งความเร็วในการตอบสนองและความสามารถในการทำงานกับ infrastructure ที่ใช้เวลานาน

## ความสัมพันธ์กับข้อมูลและบริการประกอบ

`Momoi` ใช้ PostgreSQL เป็น source of truth ของแพลตฟอร์ม และใช้ Redis เป็นทั้ง cache และ queue broker การมีสองบทบาทนี้ใน Redis มีผลอย่างมากต่อการ debug เพราะเมื่อระบบ queue มีปัญหา ต้องแยกให้ออกว่าเป็นปัญหาการส่งงานหรือปัญหาการ cache ข้อมูลเก่า

ฝั่ง storage `Momoi` ยังเชื่อมกับ object storage provider เพื่อออก URL สำหรับ upload และ download รวมถึงดูแล metadata และ permission model ที่สัมพันธ์กับผู้ใช้จริง

ฝั่ง monitoring `Momoi` ทำหน้าที่เหมือน gateway ที่เปิดให้ frontend ดึงข้อมูล query ได้ในกรอบที่ควบคุมได้ แทนที่จะให้ UI ติดต่อกับระบบ observability โดยตรง

## สิ่งที่ Momoi ส่งต่อให้ Yuzu

สำหรับงานเกี่ยวกับ VM lifecycle `Momoi` ทำหน้าที่เพียงบางส่วนเท่านั้น มันจะเป็นผู้ตัดสินใจทางธุรกิจ เช่น ตรวจว่าคำร้องผ่านหรือยัง ผู้ใช้มีสิทธิ์หรือไม่ ข้อมูลครบหรือยัง จากนั้นจะบันทึกสถานะลงฐานข้อมูลและ enqueue งานไปยัง `Yuzu`

เมื่อถึงขั้นตอนนี้ `Momoi` ไม่ได้ควบคุม provisioning ด้วยตัวเองอีกต่อไป แต่ยังคงเป็นศูนย์กลางของความหมายเชิงธุรกิจ เช่น instance นี้เกิดจากคำร้องใด อยู่ในสถานะใด ใครเป็นเจ้าของ และงานล่าสุดสำเร็จหรือล้มเหลวอย่างไร

## ผลลัพธ์ที่ควรจะเป็นเมื่อ Momoi ทำงานถูกต้อง

ถ้า `Momoi` อยู่ในสภาพสมบูรณ์ ควรเห็นสิ่งต่อไปนี้

- API พร้อมตอบคำขอทั้งฝั่งผู้ใช้ทั่วไปและฝั่งผู้ดูแล
- frontend ดึงข้อมูล dashboard, requests, instances, storage และ admin views ได้จริง
- auth flow ที่ environment นั้นใช้อยู่ตอบกลับได้สอดคล้องกับการตั้งค่า
- งานที่ต้องใช้ worker ถูก enqueue อย่างถูกต้อง
- cache ไม่ทำให้ผู้ใช้เห็นข้อมูลเก่าเกินจำเป็น
- storage operations ทำงานได้ทั้ง metadata layer และ object storage layer
- monitoring endpoints ตอบกลับข้อมูลที่ frontend ใช้สร้างแดชบอร์ดได้
- OpenAPI สามารถสะท้อนสัญญาของระบบให้ frontend ใช้งานต่อได้

## อาการเสียที่มักโยงมาที่ Momoi

ปัญหาที่มักชี้มาที่ `Momoi` มีตั้งแต่ระดับง่ายไปจนถึงระดับเชิงสถาปัตยกรรม

- login ผ่านแต่เรียก business API ไม่ได้
- หน้า requests หรือ instances โหลดไม่ขึ้นทั้งที่ frontend ยังเปิดได้
- สั่งอนุมัติคำร้องแล้วไม่มีงานเข้า queue
- ข้อมูลใน dashboard ไม่อัปเดตเพราะ cache ไม่ถูกล้าง
- storage upload ได้แต่ create metadata ไม่ผ่าน หรือกลับกัน
- monitoring dashboard ใน frontend ว่าง เพราะ gateway ดึงข้อมูลไม่ได้
- API ตอบช้าผิดปกติจาก query หนัก, storage integration หรือ upstream observability ช้า

เมื่อเห็นอาการเหล่านี้ การดูเพียง response error ไม่พอ ควรดูทั้ง database state, queue state, cache behavior และ telemetry ประกอบกัน

## จุดที่ควรระวังใน code base ปัจจุบัน

เรื่องแรกคือ auth topology ในภาพเอกสารบางส่วน `Momoi` ถูกเล่าเป็นเจ้าของ auth โดยตรง แต่ใน workspace จริงยังมี `Arisu` อยู่ ดังนั้นหากกำลัง debug เรื่อง login ต้องรู้ก่อนว่า environment ปัจจุบันกำลังใช้ auth path แบบไหน

เรื่องที่สองคือ queue stack ปัจจุบันใช้ Redis และ BullMQ แล้ว ความเข้าใจเดิมที่คิดว่าระบบใช้ RabbitMQ จะทำให้ไล่ปัญหาผิดทางทันที

เรื่องที่สามคือ `Momoi` มีโดเมนเยอะมาก การเปลี่ยนกฎในจุดหนึ่งอาจกระทบหลายหน้าจอพร้อมกัน เช่น การเปลี่ยน schema ของ request อาจกระทบทั้งการแสดงผลใน `Midori`, การ enqueue ไป `Yuzu`, และการเก็บ audit log

## ขอบเขตที่ Momoi ไม่ควรแบกรับ

แม้ `Momoi` จะเป็นสมองหลักของระบบ แต่มันไม่ควรเป็นผู้ลงมือแตะ Proxmox โดยตรงหรือเป็นผู้สร้างไฟล์ Nginx config เอง งานประเภทนั้นควรอยู่ที่ `Yuzu` และ `Satsuki` เพราะต้องการบริบทด้าน infrastructure และข้อจำกัดเชิงปฏิบัติการที่ต่างกัน

การคงขอบเขตนี้ไว้ทำให้ `Momoi` เป็นศูนย์กลางของความหมายและกฎธุรกิจ โดยไม่กลายเป็น service ที่รวมทุกความรับผิดชอบไว้จนดูแลยาก

## ความสัมพันธ์กับ repository อื่น

`Momoi` รับคำสั่งจาก `Midori`, ใช้ PostgreSQL กับ Redis เป็นฐานสำคัญของระบบ, ส่งงานต่อไปยัง `Yuzu`, เชื่อมข้อมูลบางส่วนที่มีผลต่อ `Satsuki`, และพึ่งพา environment กับ topology ที่ถูกกำหนดไว้ใน `Yuuka` ส่วน `Arisu` เป็นตัวอย่างของ auth topology ที่ยังอาจอยู่คู่กับ `Momoi` ในบาง environment

## สรุปสั้น

`Momoi` คือสมองของแพลตฟอร์ม มันเป็นจุดที่แปลงเจตนาของผู้ใช้ให้กลายเป็นกฎธุรกิจ สถานะข้อมูล และคำสั่งไปยังระบบ execution ถ้าต้องการเข้าใจว่าระบบ “คิด” อย่างไร ให้เริ่มจาก repository นี้
