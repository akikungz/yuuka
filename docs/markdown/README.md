# Cloud-Based Platform Repository Docs

## เป้าหมายของเอกสารชุดนี้

เอกสารชุดนี้เขียนขึ้นเพื่ออธิบายระบบ Cloud-Based Platform ในระดับที่คนใหม่สามารถอ่านแล้วเข้าใจภาพรวมได้โดยไม่ต้องเปิดเอกสารอื่นต่อ จุดตั้งต้นสำคัญคือระบบนี้ไม่ได้เป็น monorepo แต่เป็นแพลตฟอร์มที่ประกอบจากหลาย repository ซึ่งแต่ละตัวมีหน้าที่ชัดเจนและวงจรชีวิตของตัวเอง

สิ่งที่เอกสารชุดนี้พยายามตอบให้ครบในทุก repository คือ

1. repository นั้นรับผิดชอบอะไรในระบบ
2. มันเชื่อมกับส่วนอื่นอย่างไร
3. เมื่อมันทำงานถูกต้องควรเห็นผลลัพธ์แบบไหน
4. ถ้ามันมีปัญหา อาการจะออกมาในรูปแบบใด
5. มีจุดไหนที่ code base ปัจจุบันสะท้อนความจริงมากกว่าคำอธิบายเชิงเอกสารเดิม

เอกสารนี้จึงเหมาะทั้งสำหรับ onboarding, architecture review, troubleshooting และการทำความเข้าใจว่าระบบจริงใน workspace ปัจจุบันประกอบด้วยอะไรบ้าง

## ภาพใหญ่ของแพลตฟอร์ม

แพลตฟอร์มนี้มีเป้าหมายหลักคือให้ผู้ใช้ในบริบทการเรียนการสอนสามารถร้องขอ ใช้งาน และดูแลทรัพยากรเครื่องเสมือนได้ผ่านเว็บ โดยมีระบบหลังบ้านคอยจัดการ provisioning, lifecycle, storage, reverse proxy, SSH access และ observability อย่างครบถ้วน

ถ้ามองในเชิงบทบาท repository หลักสามารถสรุปได้ดังนี้

- `Midori` เป็น frontend หลักที่ผู้ใช้ใช้งานโดยตรง
- `Momoi` เป็น API หลักและศูนย์รวม business logic
- `Yuzu` เป็น worker ที่ลงมือทำงานกับ Proxmox VE จริง
- `Satsuki` เป็น automation service บนเครื่อง Nginx ภายนอกสำหรับ reverse proxy และ SSH access
- `Yuuka` เป็นชั้น deployment, observability, environment และเอกสารระบบ
- `Arisu` เป็น auth service แยกที่ยังมีอยู่จริงใน code base
- `Testing` เป็น utility repo สำหรับทดสอบระบบจากมุมผู้ใช้
- `Renako` เป็น repo ทดลองหรือ placeholder ที่ยังไม่เข้าไปอยู่ใน runtime หลัก

## สองชั้นสำคัญของระบบ

ถ้าอยากเข้าใจระบบแบบไม่หลงรายละเอียด ควรแบ่งความคิดออกเป็นสองชั้น

ชั้นแรกคือ control plane หรือชั้นที่รับคำสั่งและตัดสินใจเชิงธุรกิจ ซึ่งประกอบด้วย `Midori` และ `Momoi` เป็นหลัก ผู้ใช้เข้าสู่ระบบจากฝั่งเว็บ เห็นข้อมูล ตัดสินใจส่งคำสั่ง และให้ backend ตรวจสิทธิ์กับบันทึกสถานะลงฐานข้อมูล

ชั้นที่สองคือ execution plane หรือชั้นที่ลงมือทำงานกับ infrastructure จริง ซึ่งประกอบด้วย `Yuzu` และ `Satsuki` เป็นหลัก เมื่อ backend ตัดสินแล้วว่างานใดควรเกิดขึ้น งานจะถูกแปลงเป็นคิวหรือการเปลี่ยนสถานะในฐานข้อมูล จากนั้น worker และ automation service จะนำไปเปลี่ยนแปลงโลกจริง เช่น สร้าง VM, ลบ VM, สร้าง reverse proxy route, หรืออัปเดต `authorized_keys`

`Yuuka` เป็น repository ที่คร่อมอยู่ระหว่างสองชั้นนี้ เพราะมันไม่ได้เป็น service runtime โดยตรง แต่เป็นที่เก็บ topology ของระบบทั้งหมด ทั้งการเริ่มบริการประกอบ การ deploy และการสังเกตการณ์ระบบ

## เส้นทางการทำงานหลักของผู้ใช้

ลำดับการทำงานแบบทั่วไปของระบบสามารถอธิบายได้ดังนี้

1. ผู้ใช้เข้าระบบผ่าน `Midori`
2. frontend ตรวจ session และสิทธิ์ของผู้ใช้
3. frontend เรียก `Momoi` เพื่ออ่านข้อมูล เช่น รายการคำร้อง เครื่องเสมือน ไฟล์ หรือข้อมูลผู้สอน
4. เมื่อผู้ใช้สั่งงานที่ต้องใช้ตรรกะธุรกิจ เช่น ขอสร้างเครื่อง ขอขยายเวลา หรือเปลี่ยนสถานะเครื่อง คำสั่งจะถูกส่งไปยัง `Momoi`
5. `Momoi` ตรวจสิทธิ์ ตรวจเงื่อนไข และบันทึกผลลง PostgreSQL
6. หากงานนั้นใช้เวลานานหรือแตะ infrastructure จริง `Momoi` จะส่ง job เข้า Redis/BullMQ
7. `Yuzu` ดึงงานจากคิวแล้วไปจัดการ VM บน Proxmox VE
8. เมื่อข้อมูลด้าน reverse proxy หรือ SSH access เปลี่ยน `Satsuki` จะตรวจจับการเปลี่ยนแปลง สร้างไฟล์ config ใหม่ และ reload Nginx บนเครื่องภายนอก
9. ผู้ใช้กลับมาเห็นผลลัพธ์ผ่าน `Midori` ซึ่งอ่านสถานะล่าสุดจาก `Momoi`

สิ่งที่ควรสังเกตคือผู้ใช้ไม่ได้คุยกับ `Yuzu` หรือ `Satsuki` โดยตรง แต่ประสบการณ์ปลายทางที่ผู้ใช้ได้รับขึ้นอยู่กับสองส่วนนี้มาก

## บริการประกอบที่ระบบพึ่งพา

แม้ repository หลักจะมีไม่กี่ตัว แต่ระบบจะทำงานไม่ได้เลยหากบริการประกอบเหล่านี้ไม่พร้อม

- PostgreSQL เป็นแหล่งข้อมูลหลักของระบบ
- Redis เป็นทั้ง cache และ message broker สำหรับคิว
- object storage แบบ S3-compatible ใช้กับการจัดเก็บไฟล์
- Prometheus, Grafana, Loki, Jaeger และ OTEL stack ใช้กับ observability
- Proxmox VE เป็นปลายทางของงาน provision และ lifecycle ของ VM
- Nginx บนเครื่องภายนอกเป็นด่าน reverse proxy ที่ทำให้ผู้ใช้เข้าถึงบริการใน VM ได้จริง

ดังนั้นเวลาระบบมีปัญหา บางครั้งสาเหตุไม่ได้อยู่ใน application code โดยตรง แต่อยู่ที่บริการประกอบที่ขาดหรือ config ไม่ตรงกัน

## สถานะของ code base ปัจจุบัน

มีหลายจุดที่ควรรู้ก่อนอ่านเอกสารราย repository เพราะเป็นจุดที่มักทำให้คนใหม่สับสน

จุดแรกคือเรื่อง auth topology ใน narrative ปัจจุบันของเอกสารโครงงาน มีแนวโน้มอธิบาย auth อยู่ภายใต้ `Momoi` มากขึ้น แต่ code base ใน workspace ยังมี `Arisu` เป็น auth service แยกจริง ดังนั้นเวลาวิเคราะห์ระบบต้องแยกให้ออกว่าเรากำลังพูดถึง “ภาพในเอกสาร” หรือ “ภาพใน environment ปัจจุบัน”

จุดที่สองคือระบบคิวปัจจุบันใช้ Redis และ BullMQ แล้ว ความเข้าใจแบบเก่าที่อิง RabbitMQ จะไม่ตรงกับของจริง

จุดที่สามคือ `Yuzu` รุ่นปัจจุบันมีทั้ง per-queue concurrency และ distributed locking ดังนั้น throughput ไม่ได้ขึ้นอยู่กับจำนวน pod เพียงอย่างเดียว แต่ขึ้นกับค่า concurrency และรูปแบบการชนกันของ resource ด้วย

จุดที่สี่คือ `Satsuki` ไม่ใช่ service สำหรับเว็บทั่วไป แต่มันเป็น daemon บนเครื่อง reverse proxy ภายนอกที่มีสิทธิ์สร้าง config และ reload Nginx จริง

## กลุ่มของ repository ใน workspace

ถ้าแบ่งตามระดับความสำคัญต่อระบบที่กำลังรันอยู่จริง สามารถมองได้เป็นสามกลุ่ม

กลุ่มแรกคือ runtime หลักของแพลตฟอร์ม ได้แก่ `Midori`, `Momoi`, `Yuzu` และ `Satsuki` ถ้าหนึ่งในกลุ่มนี้ทำงานผิดปกติ ผู้ใช้จะรู้สึกได้ทันที ไม่ว่าจะเป็นการใช้หน้าเว็บไม่ได้ การสร้างเครื่องไม่สำเร็จ หรือเข้าถึงเครื่องปลายทางไม่ได้

กลุ่มที่สองคือ environment และ operations ได้แก่ `Yuuka` เพราะเป็นแหล่งรวม compose, manifests, observability และเอกสาร การไม่มี repo นี้ไม่ได้ทำให้ logic ธุรกิจหายไป แต่จะทำให้ทีมติดตั้ง ดูแล และ debug ระบบลำบากขึ้นมาก

กลุ่มที่สามคือ auxiliary repositories ได้แก่ `Arisu`, `Testing` และ `Renako` ซึ่งบางตัวสะท้อนโครงสร้างจริงที่ยังอยู่ใน code base บางตัวช่วยเรื่องทดสอบ และบางตัวเป็นเพียง placeholder ที่ยังไม่เข้า production topology

## ผลลัพธ์ที่ควรเห็นเมื่อทั้งระบบทำงานถูกต้อง

ถ้าระบบทั้งชุดอยู่ในสภาพพร้อมใช้งาน ควรเห็นภาพรวมดังนี้

- ผู้ใช้ login เข้าเว็บได้และเห็นหน้าจอตามสิทธิ์ของตน
- สามารถสร้างคำร้อง ดูคำร้อง อนุมัติคำร้อง และติดตามสถานะได้
- เมื่อคำร้องถูกอนุมัติ ระบบสามารถสร้าง VM จริงและแสดงสถานะกลับมาได้
- ผู้ใช้เชื่อมต่อเข้าเครื่องผ่าน reverse proxy หรือ SSH ได้ตามสิทธิ์
- พื้นที่จัดเก็บไฟล์ใช้งานได้จริงทั้งการอัปโหลด ดาวน์โหลด และกำหนดสิทธิ์
- ทีมพัฒนามองเห็น metrics, logs และ traces ได้ใน observability stack
- เมื่อส่วนใดส่วนหนึ่งพัง ทีมสามารถไล่หาจุดเสียจาก repository ที่รับผิดชอบได้ค่อนข้างตรงตัว

## วิธีอ่านเอกสารชุดนี้ให้คุ้มที่สุด

ถ้าต้องการเข้าใจระบบจากมุมผู้ใช้ ให้เริ่มจาก `Midori` แล้วตามด้วย `Momoi`

ถ้าต้องการเข้าใจระบบจากมุมงานที่เกิดกับ VM จริง ให้ต่อจาก `Momoi` ไป `Yuzu` แล้วตามด้วย `Satsuki`

ถ้าต้องการเข้าใจ deployment, observability และ environment ให้ดู `Yuuka`

ถ้าต้องการเข้าใจสิ่งที่ยังมีอยู่จริงใน code base แม้ไม่ใช่ narrative หลัก ให้ดู `Arisu`, `Testing` และ `Renako`

## สรุปสั้น

เอกสารโฟลเดอร์นี้ตั้งใจทำหน้าที่เป็นคำอธิบายระบบแบบ self-contained แต่ละไฟล์อธิบาย repository หนึ่งตัวให้จบในตัวเอง และ README ฉบับนี้ทำหน้าที่เชื่อมทุกส่วนเข้าด้วยกันเพื่อให้เห็นว่าระบบทั้งแพลตฟอร์มขยับจากคำสั่งของผู้ใช้ไปสู่การเปลี่ยนแปลงบน infrastructure จริงได้อย่างไร
