# Arisu

## ภาพรวม

`Arisu` เป็น auth service แยกที่ยังมีอยู่จริงใน workspace ปัจจุบัน แม้มันจะไม่ใช่แกนหลักของ narrative เอกสารบางชุดแล้ว แต่ในมุมของ code base มันยังเป็นระบบยืนยันตัวตนที่สมบูรณ์พอจะทำงานได้ด้วยตัวเอง

ความสำคัญของ `Arisu` คือมันแสดงให้เห็นว่าระบบนี้เคยหรือยังสามารถวาง auth topology แบบแยก service ได้จริง ไม่ได้เป็นเพียงแนวคิดที่อยู่ในอดีต

## บทบาทของ Arisu ในเชิงระบบ

หน้าที่หลักของ `Arisu` คือจัดการ authentication และ session โดยแยกออกจาก business API ส่วนอื่น มันรับคำขอด้าน sign-in, sign-up, session validation และ flows ที่เกี่ยวกับการยืนยันตัวตน จากนั้นจึงบันทึกและอ่านข้อมูลที่เกี่ยวข้องจากฐานข้อมูลของตัวเอง

เมื่อแยก auth ออกมาในรูปนี้ จุดแข็งคือสามารถแยกวงจรชีวิตของระบบยืนยันตัวตนออกจาก business API ได้ชัดขึ้น แต่ก็ต้องแลกกับความซับซ้อนเรื่อง environment, cookies, callback URL และการเชื่อมระหว่าง frontend กับ backend อื่น

## ลักษณะสำคัญของ implementation

`Arisu` ใช้ stack ที่เบากว่า `Momoi` แต่มีโครงสร้างครบในฐานะ standalone service มี web framework, auth library, database layer, metrics, logging และ telemetry ของตัวเอง

สิ่งที่น่าสนใจคือ service นี้ไม่ได้เพียงเปิด endpoint พื้นฐาน แต่ยังมี domain rule เกี่ยวกับผู้ใช้จริง เช่น การตรวจรูปแบบอีเมลของนักศึกษา การแยก instructor ออกจาก student และการผูก role ของผู้ใช้กับข้อมูลในระบบ

ดังนั้น `Arisu` ไม่ได้เป็น auth gateway แบบ generic ล้วน ๆ แต่มีตรรกะที่รู้จักบริบทขององค์กรและผู้ใช้จริงอยู่พอสมควร

## กฎธุรกิจด้านผู้ใช้ที่พบใน Arisu

จากโค้ดปัจจุบันเห็นชัดว่า `Arisu` มีแนวคิดเรื่องประเภทผู้ใช้ฝังอยู่ ไม่ว่าจะเป็นนักศึกษา ผู้สอน หรือผู้ดูแล ระบบตรวจรูปแบบอีเมลบางชุดเพื่อคัดกรองว่าผู้ใช้มาจากกลุ่มที่อนุญาตหรือไม่ และยังมี logic ที่เกี่ยวกับการจัด role ให้สอดคล้องกับข้อมูลในระบบ

จุดนี้สำคัญเพราะหมายความว่าใน auth topology แบบแยก service กฎเรื่องตัวตนของผู้ใช้ไม่ได้อยู่แค่ใน business API แต่บางส่วนถูกผลักมาอยู่ใน service นี้ด้วย

## ลำดับการทำงานโดยทั่วไป

ลำดับมาตรฐานของ `Arisu` มักเป็นดังนี้

1. รับคำขอด้าน sign-in, sign-up หรือ session
2. ตรวจข้อมูลรับเข้าตามกฎของ auth library และเงื่อนไขของแพลตฟอร์ม
3. ตรวจว่าผู้ใช้ตรงกับนโยบายด้านอีเมลและ role หรือไม่
4. อ่านหรือเขียนข้อมูลในฐานข้อมูล auth
5. สร้างหรืออัปเดต session
6. ส่ง cookie หรือผลลัพธ์ของ auth flow กลับไปยัง caller
7. เก็บ metrics และ telemetry ของคำขอนั้น

ในมุมนี้ `Arisu` เป็นทั้ง auth gateway และ policy enforcement layer สำหรับเรื่องตัวตนของผู้ใช้

## ผลลัพธ์ที่ควรจะเป็นเมื่อ Arisu ทำงานถูกต้อง

ถ้า `Arisu` อยู่ในสภาพพร้อมใช้งาน ควรเห็นผลดังนี้

- service start ได้และพร้อมตอบคำขอด้าน auth
- sign-in และ sign-up ที่นโยบายอนุญาตทำได้
- session ถูกสร้าง ตรวจสอบ และใช้งานต่อได้
- ผู้ใช้ได้รับ role ที่สอดคล้องกับกฎของระบบ
- metrics และ telemetry ของ service พร้อมสำหรับการสังเกตการณ์

## อาการที่มักบอกว่า Arisu มีปัญหา

ปัญหาที่มักโยงมาที่ `Arisu` ได้แก่

- login ไม่ผ่านทั้งที่ business API ตัวอื่นยังใช้งานได้
- ผู้ใช้ถูกปฏิเสธเพราะกฎเรื่องอีเมลหรือ role mapping
- session ถูกสร้างไม่สมบูรณ์หรือ cookie ไม่ทำงานตามที่คาด
- frontend ชี้ไปยัง auth service นี้ แต่ environment ที่รันจริงไม่ได้ตั้งค่ารองรับครบ
- ระบบบางส่วนคิดว่า auth อยู่ใน `Momoi` แต่ runtime จริงกลับใช้ `Arisu`

## สถานะของ Arisu เมื่อเทียบกับภาพรวมของแพลตฟอร์ม

ในระดับ code base `Arisu` ยังเป็นของจริงที่พร้อมทำงาน แต่ในระดับ narrative ล่าสุดของเอกสารโครงงาน มันถูกลดบทบาทลงและ auth ถูกเล่ากลับไปอยู่ใต้ `Momoi` มากขึ้น

ความจริงสองชุดนี้ไม่จำเป็นต้องขัดกันเสมอไป เพราะอาจสะท้อนช่วงเปลี่ยนผ่านของสถาปัตยกรรม แต่สำหรับคนที่กำลัง debug ระบบ สิ่งสำคัญคืออย่าคิดว่า auth topology มีรูปแบบเดียว

## เมื่อใดควรสนใจ Arisu

ถ้ากำลังไล่ปัญหา login, callback, cookies, session persistence, role mapping หรือความไม่ตรงกันระหว่าง frontend กับ auth backend `Arisu` เป็น repository ที่ควรถูกหยิบมาดูทันที โดยเฉพาะเมื่อ environment นั้นยังใช้งาน auth service แยก

ถ้า environment ไม่ได้ใช้ `Arisu` เป็นตัวหลัก มันก็ยังมีคุณค่าในฐานะหลักฐานทางสถาปัตยกรรมว่าระบบนี้เคยหรือยังรองรับการแยก auth ออกจาก core API จริง

## สรุปสั้น

`Arisu` คือ auth service แยกที่ยังมีตัวตนชัดใน code base มันสำคัญไม่ใช่เพราะเป็น narrative หลักของเอกสารปัจจุบัน แต่เพราะมันบอกความจริงของ auth topology ที่ยังอาจมีผลต่อการ deploy และการ debug ระบบในโลกจริง
