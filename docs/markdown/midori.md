# Midori

## ภาพรวม

`Midori` เป็น frontend หลักของแพลตฟอร์มและเป็นส่วนที่ผู้ใช้รับรู้ได้โดยตรงมากที่สุด ทุกอย่างที่ผู้ใช้มองเห็น ตั้งแต่หน้าแรก หน้าลงชื่อเข้าใช้ dashboard รายการคำร้อง รายการเครื่องเสมือน พื้นที่เก็บไฟล์ ไปจนถึงหน้าสำหรับผู้ดูแล ล้วนถูกส่งผ่าน repository นี้

ในเชิงสถาปัตยกรรม `Midori` ไม่ได้เป็นแค่หน้าจอสวยงาม แต่เป็นชั้นที่ทำหน้าที่แปล business capability ของระบบให้กลายเป็นประสบการณ์ใช้งานจริง มันต้องเข้าใจ role ของผู้ใช้ รู้ว่าควรดึงข้อมูลอะไร แสดงผลในรูปแบบใด และตอบสนองต่อเหตุการณ์ที่มีทั้งแบบ synchronous และ asynchronous ได้อย่างชัดเจน

## บทบาทของ Midori ในระบบ

หน้าที่หลักของ `Midori` มีอยู่สี่มิติ

มิติแรกคือการยืนยันตัวตนและการนำทาง ผู้ใช้เข้ามาในระบบผ่านหน้าเว็บนี้ ระบบต้องตรวจ session รู้ว่าผู้ใช้เป็นใคร และพาไปยังปลายทางที่เหมาะกับสิทธิ์ของคนนั้น

มิติที่สองคือการแสดงข้อมูล `Midori` ต้องดึงข้อมูลจาก backend แล้วแสดงเป็นรายการที่ผู้ใช้เข้าใจได้ เช่น คำร้องที่รออนุมัติ เครื่องที่ถูกสร้างแล้ว สถานะการทำงานย้อนหลัง รายการไฟล์ หรือภาพรวมการใช้งานระบบ

มิติที่สามคือการรับคำสั่งจากผู้ใช้ ไม่ว่าจะเป็นการสร้างคำร้อง อนุมัติหรือปฏิเสธคำร้อง ขอขยายเวลา จัดการไฟล์ เพิ่ม SSH key หรือสั่งงานเกี่ยวกับเครื่องเสมือน

มิติที่สี่คือการอธิบายสถานะของระบบกลับไปยังผู้ใช้ เพราะในแพลตฟอร์มนี้หลายงานไม่ได้เสร็จทันที เมื่อ backend ส่งงานเข้า queue แล้ว `Midori` ต้องทำให้ผู้ใช้เข้าใจว่า “คำสั่งถูกส่งแล้ว”, “กำลังดำเนินการ”, “สำเร็จ”, หรือ “ล้มเหลวเพราะอะไร”

## กลุ่มผู้ใช้และหน้าจอหลัก

จากโครงสร้างของระบบปัจจุบัน เห็นได้ชัดว่า `Midori` ถูกออกแบบมารองรับผู้ใช้หลายบทบาท ไม่ใช่เว็บหน้าเดียวสำหรับทุกคน

กลุ่มแรกคือนักศึกษา ซึ่งเป็นผู้สร้างคำร้อง ดูสถานะเครื่องของตัวเอง จัดการ SSH key และใช้งานพื้นที่เก็บไฟล์

กลุ่มที่สองคืออาจารย์หรือผู้สอน ซึ่งมีสิทธิ์ในการดูและอนุมัติคำร้องบางประเภท ดูเครื่องของผู้เรียนในขอบเขตที่ตนดูแล และอาจต้องใช้ข้อมูลเชิงวิชาการประกอบการตัดสินใจ

กลุ่มที่สามคือผู้ดูแลระบบ ซึ่งเห็นข้อมูลมากที่สุดและมีหน้าจอสำหรับดูแลข้อมูลพื้นฐานของระบบ เช่น รายวิชา ภาคการศึกษา รายชื่อผู้สอน รายการเมล รวมถึงหน้าจอมอนิเตอร์สถานะของ Proxmox cluster

พื้นที่ใช้งานหลักของ `Midori` จึงกระจายอยู่ในหลายโดเมน เช่น login, dashboard, requests, instances, storage, settings และ admin แต่ละส่วนไม่ได้แยกกันเพียงในระดับเมนูเท่านั้น แต่สะท้อน use case ที่แตกต่างกันของแพลตฟอร์ม

## โครงสร้างเชิงตรรกะภายใน

แม้ผู้ใช้จะเห็นเพียงหน้าเว็บ แต่ภายใน `Midori` มีการแบ่งบทบาทของโค้ดค่อนข้างชัด

มีชั้น route ที่รับผิดชอบการแบ่งหน้าและจัดการการเรนเดอร์ตามเส้นทาง มีชั้น component ที่แยกตามโดเมนของหน้าจอ มีชั้น hook สำหรับเก็บ logic ฝั่ง client ที่ใช้ซ้ำ เช่น session, role, search, filters หรือการดึงข้อมูล มีชั้น integration สำหรับ auth client, API client, environment และ telemetry และยังมีชั้น type definitions ที่ช่วยควบคุมความสอดคล้องของข้อมูลระหว่าง frontend กับ backend

แนวคิดนี้ทำให้ `Midori` ไม่ได้เป็น collection ของหน้าเว็บที่ต่อกันแบบหลวม ๆ แต่เป็นระบบ UI ที่มีสถาปัตยกรรมรองรับการเติบโตของโดเมน

## ความสามารถที่โดดเด่นในระดับฟังก์ชัน

สิ่งที่เห็นเด่นชัดใน code base ปัจจุบันคือ `Midori` ไม่ได้มีเพียงหน้าแสดงรายการธรรมดา แต่มี interaction เชิงงานจริงค่อนข้างเยอะ เช่น

- การสร้างและติดตามคำร้องขอเครื่องเสมือน
- การจัดการคำร้องขอขยายเวลา
- การดูรายละเอียดเครื่องเสมือนรายตัว
- การดู audit logs ของคำร้องและเครื่อง
- การขอ reprovision เครื่องที่ล้มเหลว
- การ promote หรือเปลี่ยนสถานะบางชนิดของ instance
- การจัดการ reverse proxy ที่ผูกกับเครื่อง
- การอัปโหลด ดาวน์โหลด ค้นหา ย้าย คัดลอก และตั้งสิทธิ์ของไฟล์ใน storage
- การเพิ่ม SSH key เพื่อเชื่อมต่อเข้า instance
- การดูข้อมูล monitoring ของคลัสเตอร์สำหรับผู้ดูแล

นี่เป็นสัญญาณว่า frontend ตัวนี้ไม่ได้เป็นเพียงหน้า CRUD ธรรมดา แต่เป็นจุดรวม use case สำคัญแทบทั้งหมดของแพลตฟอร์ม

## วิธีที่ Midori คุยกับระบบส่วนอื่น

`Midori` ใช้แนวคิดที่ค่อนข้าง disciplined ในการคุยกับ backend โดยพยายามลดการเขียนชนิดข้อมูลแบบเดาสุ่มเอง และผูกกับ API contract ที่ชัดเจน วิธีนี้สำคัญมากในระบบที่มีทั้ง request flow, instance lifecycle, storage, monitoring และ admin operations เพราะหากข้อมูลฝั่งหนึ่งเปลี่ยนโดยอีกฝั่งไม่รู้ จะเกิดปัญหาที่ตามหายากมาก

ฝั่ง client ใช้กลไกดึงข้อมูลที่มี cache และ invalidation ชัดเจน จึงไม่เพียงช่วยเรื่อง performance แต่ยังช่วยให้หน้าจอสะท้อนข้อมูลใหม่หลังจากผู้ใช้สั่งงาน เช่น หลังอนุมัติคำร้อง หลังอัปโหลดไฟล์ หรือหลังเปลี่ยนสถานะเครื่อง

ในเชิงสถาปัตยกรรมข้อมูล `Midori` จึงไม่ได้เก็บ source of truth ไว้เอง แต่รับบทเป็นหน้าต่างที่แสดงสภาพล่าสุดของ source of truth ที่อยู่ใน backend และฐานข้อมูล

## ลำดับการทำงานโดยทั่วไป

ลำดับการทำงานพื้นฐานของ `Midori` มักเป็นดังนี้

1. ผู้ใช้เปิดเว็บหรือถูก redirect เข้ามายัง route หนึ่ง
2. ระบบตรวจว่ามี session อยู่หรือไม่
3. ถ้าไม่มี session จะพาไปสู่ขั้นตอน login
4. เมื่อมี session แล้ว ระบบจะตรวจ role และเลือกหน้า dashboard หรือหน้าฟังก์ชันที่เหมาะสม
5. หน้าจอจะเริ่มยิงคำขอไปยัง backend ตามข้อมูลที่หน้าจอนั้นต้องใช้
6. เมื่อผู้ใช้ส่งคำสั่ง ระบบจะเรียก API ที่เกี่ยวข้อง
7. ถ้าคำสั่งนั้นตอบกลับได้ทันที หน้าจอจะอัปเดตผลลัพธ์โดยตรง
8. ถ้าคำสั่งนั้นเป็นงานระยะยาว เช่น provisioning ระบบจะบอกสถานะให้ผู้ใช้รับรู้และรอให้ข้อมูลฝั่ง backend อัปเดต

flow นี้ดูเหมือนตรงไปตรงมา แต่ในความจริงมีความละเอียดหลายจุด เช่น การ redirect หลัง login การป้องกันผู้ใช้เห็นหน้าที่ไม่ควรเห็น การ refresh query หลัง mutation และการแสดง feedback ที่พอจะใช้ debug ได้เมื่อ backend ตอบกลับ error

## ผลลัพธ์ที่ควรจะเป็นเมื่อ Midori ทำงานถูกต้อง

ถ้า `Midori` ทำงานสมบูรณ์ ผู้ใช้ควรได้รับประสบการณ์ดังต่อไปนี้

- เปิดหน้าเว็บแล้วได้หน้า landing หรือหน้า dashboard อย่างเสถียร
- login แล้วไม่เกิดการ redirect loop
- ผู้ใช้แต่ละ role เห็นเมนูและข้อมูลตามสิทธิ์จริง
- คำร้องและเครื่องเสมือนแสดงสถานะสอดคล้องกับ backend
- หลังผู้ใช้กดสั่งงาน หน้าจอแสดงผลลัพธ์หรือสถานะต่อเนื่องที่เข้าใจได้
- หน้าจอ storage ใช้งานได้จริงทั้งค้นหา อัปโหลด ดาวน์โหลด และกำหนดสิทธิ์
- หน้าผู้ดูแลดึงข้อมูลเชิงวิชาการและ monitoring ได้
- เมื่อ backend ทำงานช้าหรือเป็นงาน async ผู้ใช้ยังเข้าใจได้ว่าระบบกำลังทำอะไรอยู่

## อาการที่มักบอกว่า Midori มีปัญหา

อาการที่เจอบ่อยและควรสงสัย `Midori` ก่อนมีหลายแบบ

- หน้าเว็บขึ้นได้แต่ข้อมูลไม่โหลดเลย
- login สำเร็จแต่ยังค้างอยู่หน้าเดิมหรือเด้งวนไปมา
- ผู้ใช้เห็นเมนูไม่ตรงกับ role ของตัวเอง
- action สำเร็จใน backend แต่หน้าจอไม่ refresh
- โครงสร้างข้อมูลจาก backend เปลี่ยนแล้วทำให้หน้าใดหน้าหนึ่งพังใน runtime
- หน้าจอแสดงสถานะ provisioning ผิดจากของจริง ทำให้ผู้ใช้เข้าใจว่าระบบค้าง
- เส้นทาง auth ที่ frontend ใช้ไม่ตรงกับ topology ของ environment นั้น

เมื่อเกิดอาการเหล่านี้ ต้องแยกให้ได้ว่าเป็นปัญหา UI state, API contract, auth integration หรือ environment mismatch

## ขอบเขตที่ Midori ไม่ควรรับผิดชอบ

แม้ `Midori` จะมีบทบาทมาก แต่มันไม่ควรเป็นผู้ตัดสิน business rule เชิงลึก เช่น ใครมีสิทธิ์อนุมัติคำร้องขั้นสุดท้าย จะเลือก Proxmox node ไหน จะสร้าง VM อย่างไร หรือจะออก route reverse proxy แบบไหน

ถ้าพบ logic ประเภทนี้ฝังอยู่ใน frontend มากเกินไป จะทำให้ระบบรักษาความถูกต้องยากและเสี่ยงเกิดการตีความไม่ตรงกันระหว่าง UI กับ backend

## จุดที่ควรระวังใน code base ปัจจุบัน

เรื่องที่ต้องระวังที่สุดคือ auth topology เพราะในคำอธิบายเชิงสถาปัตยกรรมบางชุดมีการรวม auth กลับเข้าไปอยู่ใต้ `Momoi` แต่ใน workspace ปัจจุบันยังมีร่องรอยชัดเจนว่าบาง environment สามารถชี้ `Midori` ไปยัง auth service แยกได้

ดังนั้นเวลาวิเคราะห์ปัญหา login, cookies, callback หรือ session ต้องดู environment จริงเสมอ และอย่าตัดสินจาก frontend เพียงฝั่งเดียว

อีกจุดหนึ่งคือ `Midori` พึ่งพา API contract อย่างมาก หากฝั่ง backend เปลี่ยน endpoint, payload หรือ rule ของ field โดยไม่อัปเดตฝั่งเว็บทันที ผลกระทบจะไปโผล่ที่หน้าจอเร็วมาก

## ความสัมพันธ์กับ repository อื่น

`Midori` พึ่งพา `Momoi` สำหรับ business API แทบทั้งหมด พึ่งพา auth backend ตาม environment ที่เลือกใช้งาน สะท้อนผลลัพธ์ของงานที่ `Yuzu` ทำอยู่เบื้องหลัง และแสดงข้อมูลที่มีผลจาก `Satsuki` เช่น reverse proxy หรือ SSH access ทางอ้อม ส่วน topology การติดตั้ง การตั้งค่า service URLs และ environment โดยรวมขึ้นกับสิ่งที่ถูกกำหนดใน `Yuuka`

## สรุปสั้น

`Midori` คือจุดที่เปลี่ยนความซับซ้อนของแพลตฟอร์มให้กลายเป็นประสบการณ์ใช้งานจริง ถ้าต้องการเข้าใจว่าผู้ใช้เริ่มตรงไหน เห็นอะไร กดอะไรได้บ้าง และรับรู้ความสำเร็จหรือความล้มเหลวของระบบอย่างไร ให้เริ่มจาก repository นี้ก่อนเสมอ
